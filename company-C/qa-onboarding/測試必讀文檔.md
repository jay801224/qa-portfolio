# 測試必讀文檔 (QA onboarding reading list)

QA 新人必讀文檔，兩部分：Jira 開單範例（每個欄位怎麼填）與 on-boarding / junior 課程清單。
公司名、產品名已替換為 `<PRODUCT>` 佔位符。

## jira開單範例

| 欄位 | 內容 |
|---|---|
| 摘要 | `[遊戲後台/內部] 遊戲動作新增時，未填寫完畢即可新增`（此為範例）。`[]` 裡面要有發現問題的環境-專案的名稱 |
| 說明 | `expect:` 四項都要填，才可新增。`actual:` 只有全空不給新增／只要動作不為空，都讓使用者新增；若是如此建議第一項新增紅色 `*`（此為範例） |
| 優先級 | priority，目前分五級：<br>**Highest** 公司名譽受損／金錢損失／重要頁面整頁故障<br>**High** 較嚴重的錯誤，可能會導致少許功能接連故障／不容易重現但是問題很嚴重的錯誤<br>**Medium** 功能異常，預設的 BUG 嚴重等級<br>**Low** 小跑版／翻譯錯誤<br>**Lowest** 不重要的文字錯誤／UI 錯誤 |
| 步驟 | 測試專案時，原則上不寫，除非步驟真的很複雜或是特殊案例 |
| 環境 | windows 10 / chrome 72.0.3626.121；ipad pro / ios 12.1.1 |
| 標籤 | labels，方便之後 filter 使用。後台按照主目錄分、前台裝置就標 IOS、ANDROID。優先：`<PRODUCT>` 專案，要標 `<PRODUCT>` 或是 彩票（`<PRODUCT>` 就標彩票）。QA 內部：按功能分就標充值／遊戲廳名（可之後再慢慢標） |
| 附加檔案 | 截圖才是最重要的，記得要有網址（靜態的問題）；影片（動態的問題） |
| 評論 | 其他資訊補充，或是哪邊也有這問題，還發現甚麼事情 |

### 備註

1. online bug / project bug / suggestion 等等，統一在 jira 上提交，方便管理，redmine 已不再使用，QA 不開 task。
2. QA 不能切 won't do 跟 resolved，resolved 驗證通過先切 verified。
3. bug / 建議請確實分清楚，建議被接受才會變成需求。
4. 若為未定義事項，請在 TG 確認，細節通常會補做，但是大功能是初期 accept，後期 reject。
5. bug 開列以需求文檔為主，但是文檔也是會有漏，在溝通上需要花點時間。
6. 手動測試要懂得發問，有問題就要問，不要只看問題的表層，要看源頭錯在哪。
7. jira 善用 board 跟 filter 去管理單號，這是價值所在。
